## 优先处理：P1

### 1. 升级被 SIGTERM 中断时丢失恢复资料

- 位置：`scripts/upgrade.sh:22,135,146,150-163`。
- 服务停止且源码替换后，仅向升级脚本 Bash PID 发送 SIGTERM，脚本退出 143，未进入 ERR 回滚；EXIT 清理删除包含恢复包的 stage。
- 沙盒实测：服务 inactive、源码标记 new、revision 仍为 oldrev、stage 数为 0。
- 影响：可留下半升级安装，并丢失本次自动恢复资料。
- 建议：明确部署事务阶段，为 INT/TERM/HUP 设计统一恢复或保留证据路径；只有成功或完整恢复才能删除恢复包。SIGKILL 无法捕获，需另外考虑恢复资料的持久保留策略。
- 证据边界：已复现直接 SIGTERM；普通 Ctrl-C 的进程组信号、SSH 断线并不必然等价。

### 2. 同一安装目录的生命周期操作缺少互斥

- 位置：`scripts/install.sh:207-223`、`scripts/uninstall.sh:109-121`、`scripts/upgrade.sh:91-163`。
- 两个具名实例安装，在读取同一旧配置后并发替换：两个 unit 均生成，最终配置只保留一个新增实例。沙盒 barrier 已复现。
- 影响：另一个 unit 对应实例配置丢失。并发卸载及升级交错还存在相同共享状态缺乏互斥的静态风险，但未逐一动态复现。
- 建议：三个脚本使用同一目录级跨进程锁，覆盖发现、配置读写、源码及 unit 操作；锁位置不能随整目录卸载而被删除。
- 不同安装目录不受这项特定丢更新竞态影响。

### 3. 浏览器入站分片缺少资源预算，取消及超时后残留

- 位置：`src/static_adapter.py:553-568,779-831`。
- 实际适配器 Node 复现：普通请求 abort 后 pending 为 0、incoming 为 1；流超时后装配残留继续增加；100 个未知 ID 的非 final 分片产生 100 条装配记录。
- 影响：连接不关闭时可持续积累内存；这不是已证实的某次用户卡顿原因。
- 建议：单消息和全局字节、条目数、TTL 预算；取消、超时、错误、完成及断线均释放装配。须区分协议 `message_id` 与业务 request/socket ID，不能仅按业务 ID 盲删。
- 严格序号检查已经存在，不属于缺失项。

## 应修复：P2

### 4. WebSocket 双向缺少有界背压

- 位置：`src/main.py:493-500,765,1027,1176-1180,1556-1559`。
- Agent 的无界 Queue 在慢上游下积压 100 帧；Gateway 向慢浏览器发送时逐帧创建 Task，100 个任务均可同时等待。受控复现及主审复跑一致。
- 建议：每 bridge 的帧数和字节预算、有界队列及单 sender；超限关闭并清理相应 bridge，避免阻塞整条共享控制通道。
- 未进行耗尽实验，不宣称已导致生产 OOM。

### 5. 并发 P2P 协商突破 peer 上限

- 位置：`src/main.py:1355-1386`。
- `max_p2p_peers=1`，两个协商均在 await 前通过数量检查，最终创建两个 peer。可由正常已认证浏览器并发连接触发。
- 建议：await 前原子预留槽位，覆盖失败、取消、关闭时的释放。

### 6. 响应未剥离 Connection 指定的逐跳头

- 位置：`src/main.py:123-133`。
- 实测 `Connection: X-Hop, keep-alive` 对应的 `X-Hop` 和 `Keep-Alive` 仍出现在过滤结果中。
- 建议：响应方向与请求方向一致，解析 Connection token 并合入禁止转发集合；补大小写及多 token 测试。

### 7. 浏览器非法 base64 帧被静默吞掉

- 位置：`src/static_adapter.py:779-800,956`。
- 实测非法编码未立即拒绝请求；真实请求 timeout 回调触发后，pending 清空但 incoming 仍残留。
- 建议：装配层捕获解码错误，清理消息，立即失败关联请求并尽力取消；与第 3 项共同修复。

### 8. 安装升级与单 Gateway 卸载文档不准确

- `README.md:37` 建议重新运行 installer 升级，但 `scripts/install.sh:110-112` 拒绝已有 unit 并要求 upgrade.sh。
- `README.md:134` 笼统描述删除安装文件；`scripts/uninstall.sh:124-127` 单 Gateway 卸载实际保留共享目录、Gateway 配置及凭据。
- 建议：升级/回滚统一指向 upgrade.sh；明确单 Gateway 卸载保留语义。保留配置符合共享目录模型，不定性为无条件凭据泄漏，也不建议为消除文档问题直接删除配置。

## 防御增强及后续验收：P3

- `src/p2p.py:204-207,268-277`：完成去重记录与装配共用 64 条容量，连续完成 65 个 ID 后首个 ID 可被重放；有效去重窗口不是无条件的 300 秒 TTL。应明确容量窗口或分离去重记录和活动装配预算。
- `src/main.py:1217-1242`：同一通道重复 request ID 可并发执行，任务字典被覆盖，取消只能命中部分工作。应 single-flight，并仅在字典仍指向自身时清理。
- 上述两项已受控复现，但当前客户端使用随机 ID、可靠有序 DataChannel，未发现自动重发已交付 mutation 的路径；不能将异常客户端重复发送等同系统自动重放事故。
- Android 构建可加强完整源码、assets manifest/hash 的强制校验；当前 README 已说明可信输入与五个入口 pin 的范围，原 P1 供应链缺陷定性撤回。
- Android `build_frontend.py:184-190` 在 notices 目录缺失时静默跳过，与 README 的携带字体声明承诺不一致；优先让必需声明缺失时构建失败。
- Android 精确 discovery 导航门禁可阻止跨端口重定向，不能只凭 auth 回调比较 host 就认定泄漏。原泄漏结论撤回，保留真实 WebView 重定向链回归需求。
- Android scheme、系统栏/insets、键盘、上传、PTY、恢复及认证缓存仍需真机/模拟器验收；SDK 编译测试在有工具链的环境中应必跑。APK 暂缓重打包是用户决定，不作为缺陷。

## 建议顺序

1. 升级中断恢复与跨脚本互斥：同属生命周期完整性，可统一设计但分别回归。
2. 浏览器入站预算、异常编码及所有终止路径清理。
3. WS 有界背压、P2P peer 原子限额和响应逐跳头。
4. 文档修正；按需求补异常客户端去重与 Android 构建、真机验证。

本报告是审查结果，不代表以上修复已完成或已获得新的功能设计批准。
